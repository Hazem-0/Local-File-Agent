2. Two-Process System Architecture & IPC Process Isolation

The application is architected around a robust Two-Process Isolation Pattern to shield the desktop user interface from potential memory leaks, corrupt PDF parser faults, or native unmanaged crashes:

Figure 1: Two-Process Isolation Architecture with Named Pipes IPC, Out-of-Process Worker, and Loopback LLM Engines

Process Isolation & Security Guarantees:

  • Crash Isolation: Untrusted document parsers (PDFium, SkiaSharp, OpenXML) run entirely inside the child LocalFileAgent.Worker process. If a corrupt file causes a crash or Out-Of-Memory, the worker terminates without affecting the UI, and automatically restarts over Named Pipes.
  • Non-Blocking Asynchronous UI: All indexing, OCR, and embedding computations execute on background thread pools with full CancellationToken support, keeping the WPF desktop interface completely responsive.
  • Strict Loopback Network Enforcement: All HTTP calls in OllamaClient validate destination endpoints before dispatch. Any address outside 127.0.0.1 or ::1 is blocked with an immediate security exception.

3. Symmetric Arabic NLP & Text Normalization Engine

The ArabicTextNormalizer forms the computational foundation of retrieval accuracy. It enforces symmetric normalization, guaranteeing that indexed document chunks and incoming user search queries undergo the exact same deterministic transformation:

Figure 2: Symmetric Arabic Text Normalization Pipeline Applied to Ingestion Chunks and User Search Queries

Text Engine Engineering Highlights:

  • Preservation of Original Text: The original text is always retained alongside the normalized copy. The desktop UI renders the original text with full diacritics, while the search indexes operate on the normalized representation.
  • Legacy Encoding Autodetection: Rather than assuming pure UTF-8, EncodingDetector inspects raw bytes, scoring Arabic character distributions across Windows-1256 (CP1256), ISO-8859-6, UTF-8, and UTF-16 to decode legacy government and business records cleanly.
  • PDF Text Quality Gate (TextQualityGate): Measures extracted digital text against readability heuristics: printable character ratio, disconnected letter frequency, and presence of unknown (cid:N) glyphs. If digital extraction fails quality thresholds, the page is rendered as an image and routed directly to OCR.

4. Multimodal Document Ingestion & Two-Tier OCR Escalation

The ingestion pipeline implements a dual-velocity architecture: the Fast Lane handles digital documents and instant native OCR, while the Slow Lane computes dense vector embeddings and AI image descriptions:

Figure 3: Multimodal Document Ingestion Pipeline with Two-Tier OCR Escalation and dHash Deduplication

Two-Tier OCR & Visual Deduplication Architecture:

  • Tier 1 — Windows Media OCR: Built-in Windows OCR engine supporting Arabic (ar-SA) and English (en-US). Runs entirely on the CPU with a benchmark latency of ~89ms per page, consuming 0 MB VRAM.
  • Tier 2 — GLM-OCR (0.9B via Ollama): Neural vision-language model invoked only for degraded documents, complex multi-column layouts, and historical manuscripts that fail Tier 1 confidence thresholds.
  • Visual Deduplication via 64-bit dHash: Before routing images to neural models, an 8x8 grayscale perceptual difference hash is computed. If the Hamming Distance is ≤ 10 compared to an existing image, cached metadata is reused in <1ms using the hardware POPCNT CPU instruction.

5. Tri-Space Hybrid Retrieval & Reciprocal Rank Fusion (RRF)

LocalFileAgent avoids single-modality pitfalls by querying three distinct retrieval spaces simultaneously, fusing the result streams via Reciprocal Rank Fusion (RRF):

Figure 4: Tri-Space Hybrid Retrieval Architecture with Reciprocal Rank Fusion (RRF) and Offset-Mapped Snippet Highlighting

Reciprocal Rank Fusion (RRF) Mathematical Formula:

The final score for candidate document chunk d across retrieval modalities M with smoothing parameter (k = 60) is calculated as: 

Score_RRF(d) = Σ [ w_m / (60 + Rank_m(d)) ]

where m denotes the retrieval space, wm is the modality weight (1.0 for Lexical, 1.2 for Dense Semantic, and 1.0 for Visual), and Rankm(d) is the 1-based rank index in that space.

Retrieval Engine Performance Features:

  • Hardware SIMD Vector Acceleration: Cosine distance across 1024-dimensional BGE-M3 embeddings is calculated via vectorized CPU intrinsics (AVX2 / Vector256 / Vector512), scoring thousands of vectors in just 22.4 ms (13.3x faster than the 300 ms SLA budget).
  • Offset-Mapped Highlighting: SnippetHighlighter matches normalized search tokens while projecting character highlight ranges onto the raw original text, ensuring diacritics and glyphs are rendered without visual distortion.

6. Local Agent Reasoning Loop & Anti-Hallucination Guardrails

The system features an autonomous local agent loop that synthesizes evidence-grounded answers from the local archive using a deterministic two-call workflow:

Figure 5: Local Agent Two-Call Sequence Diagram with Anti-Hallucination Grounding Validator

Intelligent Agent Safeguards:

  • Dialect Translation & Broken Plural Decomposition: AgentPlanner recognizes colloquial Egyptian Arabic markers ("عايز", "فين", "إزاي"), decomposes broken plurals ("فواتير" ↔ "فاتورة", "عقود" ↔ "عقد"), and filters document type requests ("بي دي اف", "وورد", "اكسل") to generate structured, deterministic search parameters.
  • Anti-Hallucination Guard (GroundingValidator): Rigorously inspects the LLM response before presentation. If the model cites any document, file path, or statistic not present in the deterministic search results, the citation is stripped and replaced with [Unverified Citation Removed], ensuring zero hallucinated information reaches the user.

7. Resource Governance, Power Management & Security Audit

Power & Battery Policy (Resource Governor & Battery Guard):

Neural vision models and dense embedding inferences demand significant processing power. To avoid battery drain during field operations, the application interfaces with the Windows kernel via GetSystemPowerStatus to enforce automated throttling:

Power State Detected Fast Lane Processing Heavy Slow Lane Processing
Connected to AC Power Full throughput (Digital parsing + Windows OCR + FTS5 indexing). Full throughput (BGE-M3 embeddings + GLM-OCR escalation + SigLIP-2).
Running on Battery Full speed (Files immediately searchable via text & Tier 1 OCR). Throttled / Paused to conserve laptop battery life and prevent thermal throttling.
Critical Battery (≤ 20%) New indexing deferred; search queries execute normally. Complete suspension of all neural model inferences.

Security Audit & Air-Gapped Compliance Standards:

Cryptographic & Architectural Security Guarantees:
  1. User File Immutability (Read-Only Invariant): Enforced via Microsoft.CodeAnalysis.BannedApiAnalyzers across all solution projects, forbidding mutating APIs (File.Delete, File.WriteAllText, Directory.Delete) outside the dedicated application data directory.
  2. Cryptographic Corpus Integrity: SHA-256 hashes of all user corpus documents are calculated before and after test executions to ensure no byte is altered.
  3. Strict Local Data Confinement: All index databases, vector tables, and logs are strictly confined within %LOCALAPPDATA%\LocalFileAgent\.

8. Desktop UI/UX Architecture & Technical Bug Resolutions

The user interface evolved across multiple engineering iterations to achieve a responsive, high-density classic desktop dialog box experience:

Figure 6: Classic Desktop Dialog Box Component Hierarchy with Dedicated Keywords Bar, Active Cards, and Aligned DataGrid

Technical Enhancements & Bug Resolutions:

  1. Strict Functional Separation of Keywords Bar: Separated the general search box from the keywords input and active tags bar, preventing secondary filters from mutating the primary search query string.
  2. Comma-Separated Multi-Input Splitting: The keyword input splits comma or semicolon separated inputs (e.g. invoice, 2025; hardware) into distinct interactive chips while automatically retaining input focus for rapid operator entry.
  3. Resolution of Duplicate File Launching Bug (Double Launch Bug):
    • Root Cause: UI buttons had both Command="{Binding OpenFileCommand}" and Click="OnOpenFileClick" wired concurrently, triggering two consecutive execution cycles on every single user click.
    • Resolution: Removed duplicate click handlers in favor of pure MVVM commands, supplemented with a thread-safe 800 ms debounce gate in SafeFileLauncher to guard against rapid successive physical clicks.
